# 商务和技术偏离表 Workflow Rules

## 1. 核心原则
- 长期 skill 只保留通用流程，不保留任何具体模板形状耦合。
- 每次先读文档，再基于语义理解决定这一次怎么拆。
- 再为这一次文件写临时脚本做确定性提取。

## 2. 仅保留一种填写思路
只保留 `demo2` 这种简单填法：
- 模板驱动
- 固定承诺句式
- 偏离表的语义拆分保留

不再保留：
- 四列表达路径模式
- 针对固定列数的分支
- 针对某个旧模板表头的长期硬编码

## 3. 长期稳定的内容
- 通用扫描能力
- 决策契约
- `rows.json` 契约
- 通用模板回填流程
- 拆分结果自检清单

## 4. 不应该长期写死的内容
- 具体列数
- 具体表头文本排列
- 具体章节编号样式
- 某一类续行合并规则
- 某一个 demo 的证据页码规则

这些都应先进入本次运行的 `decision.json`，必要时写进本次运行的临时脚本。
`decision.json` 至少应显式表达：
- source ranges
- row groups
- merge rules
- heading handling

## 5. 推荐执行顺序
1. 扫描文档结构
2. 人工/agent 语义判断
3. 形成 `decision.json`
4. 生成临时脚本
5. 运行临时脚本产出 `rows.json`
6. 用模板驱动脚本回填 docx
7. 校验结果

## 6. 语义拆分保留要求
以下内容必须继续靠语义判断，而不是模板硬编码：
- 哪个章节是偏离表来源
- 哪些标题只做分组，不单独成数据行
- 哪些要求要拆成多行
- 哪些连续段落要合并成一行
- `内容` 列该显示哪一级标签
- 哪里应该切到 `商务部分` 或 `技术部分`

## 7. 简单填法规则
- `requirement_text`：直接复制原文，尽量少改写
- `commitment_text`：固定写法 `我司完全响应并承诺满足：` + `requirement_text`
- `deviation_note`：默认 `无偏离`
- `rows.json`：只保留语义数据，不保留模板分区行、表头行、整行 cells
- 若模板要求页码或额外说明，应在本次运行的 `decision.json` 中声明，不进入长期 skill

## 8. 对 reusable script 的要求
- reusable script 只能做扫描、候选定位、模板结构识别、通用回填
- reusable script 不应替代 agent 做最终语义拆分决策
- reusable script 不应因为某个模板是 4 列、5 列或其他列数而写死分支
- reusable script 不应假设表头前后一行就是分区样板或数据样板
- 临时提取脚本应消费 `decision.json`，不应把本次运行的核心判断偷偷写死在脚本正文里

## 9. 拆分结果自检
在 `rows.json` 生成后，至少检查：
- `content` 是否脱离原上下文后仍可读
- `requirement_text` 是否被裁剪成只剩数值、短语或残句
- 是否把纯标题误当成数据行
- 是否把应合并的连续正文拆散
- 是否遗漏表格中的要求内容
- 是否遗漏商务部分或技术部分中的关键来源段落
